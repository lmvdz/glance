# R1: GitHub App wedge mechanics for gating agent-authored PRs on an external repo

Research for lmvdz/glance#325 (landing-rail campaign, tier 5). Feeds the wedge spike build ticket (#337).

## Recommendation

**Build a minimal GitHub App that posts to the Checks API, not the legacy Status API and not a required-reviewer flow.** Concretely:

- **Surface: Checks API check-run**, created/updated by the App via `POST /repos/{owner}/{repo}/check-runs` and `PATCH .../check-runs/{id}`. This is the only surface that (a) only Apps can write to, (b) supports rich markdown output (`output.summary`, `output.text`, up to 65,535 bytes each, GFM-rendered including `<details>`), and (c) can be pinned to *this app specifically* in both classic branch protection and the newer Rulesets, so a human collaborator with write access cannot spoof the receipt by hitting the old Status API.
- **Gate mechanism: Rulesets, not classic branch protection.** Add a `required_status_checks` rule whose `parameters.required_status_checks[]` entry sets both `context` (e.g. `"glance/landing-rail-receipt"`) and `integration_id` (this App's numeric ID). `integration_id` is the field that restricts the check to only-this-app; without it, any collaborator or other integration with write access can satisfy the same context string and the gate is theater. GitHub is steering new adoption toward Rulesets over classic branch protection (org-wide reuse, bypass-list audit trail, JSON import/export). Build against Rulesets from day one rather than the legacy UI.
- **Permissions (repository-scoped, single install target):**
  - `checks: write`: create/update check runs (the receipt itself).
  - `pull_requests: read`: read PR metadata (head SHA, base branch, author login, labels) to decide what to gate and to render context in the receipt.
  - `pull_requests: write`: only if the receipt is *also* mirrored as a PR comment (see below); otherwise omit to keep the grant narrow.
  - `metadata: read`: implicit/mandatory on every GitHub App, no action needed.
  - Do **not** request `contents`, `statuses` (legacy), `administration`, or `actions`: none are needed if the receipt is generated externally by the glance daemon and pushed in via API call rather than by cloning/running code inside GitHub's compute.
- **Webhooks are optional for the MVP, not load-bearing.** Because the receipt is generated *externally* by the glance daemon (which already knows the PR's head SHA when it finishes its own verification), the daemon can create the check run by direct API call, with no webhook receiver required to ship v1. Webhooks only become necessary once you want either (a) an immediate "queued/pending" check-run the instant a PR opens (subscribe to `pull_request` → `opened`/`synchronize`/`reopened`), or (b) automatic invalidation of a stale receipt when new commits land on an already-receipted PR. Recommend shipping v1 push-only (daemon-triggered), adding the `pull_request` webhook in a fast-follow once the wedge is proven live on one repo.
- **Auth flow:** standard GitHub App JWT (signed with the App's private key, `app_id` claim) exchanged for a short-lived installation access token scoped to the single repo the App is installed on (`POST /app/installations/{id}/access_tokens`). The daemon holds the App's private key + App ID as a secret and mints a fresh installation token per receipt post (installation tokens expire in 1 hour). This keeps the target repo at **zero adoption**: no workflow file, no Action, no new dependency in their CI, just an installed app plus a required check in their ruleset.
- **Why not the alternatives:**
  - *Required status check via legacy Status API* (`statuses: write`, `POST /repos/{owner}/{repo}/statuses/{sha}`): simpler, but any collaborator or integration with write access can set an arbitrary status with the same context string unless you separately configure the classic branch-protection "restrict who can push to matching branches" + app-restriction UI, which requires the app to have *already* posted at least one status/check before it's selectable as the restricting app: a bootstrapping wrinkle the Checks API doesn't have. Status API also has no structured markdown output field; you'd be jamming everything into a short "description" string capped at ~140 chars.
  - *Required reviewer (bot review)*: heavier grant (`pull_requests: write` to submit a review, potential need to appear in `CODEOWNERS` or be added as a required reviewer), and a review is a coarser signal (approve/request-changes) than a check run with per-check state (`queued`/`in_progress`/`completed` + `success`/`failure`/`neutral`/`action_required`), and it pollutes the human-reviewer UI rather than living in its own Checks tab. Save this surface for a later "the receipt itself IS the review gate" iteration, not the wedge.
  - *GitHub Action instead of a GitHub App*: rejected outright by the zero-adoption constraint. An Action requires the target repo to add a `.github/workflows/*.yml` file (or the operator to fork/PR one in) and consume the target repo's own Actions minutes: that's adoption, not a wedge. Aviator and Mergify both prove the App-only pattern works at scale (below).

## Receipt-comment format that renders best

Two channels, use both, and make the check-run authoritative:

1. **Check-run `output.summary`** (markdown, GFM-rendered in the PR's Checks tab and in the merge-box "Show all checks" popover): keep it short, one line pass/fail plus 2-4 key metrics, because the popover truncates long summaries and users rarely expand into `output.text`.
2. **Check-run `output.text`** (rendered on the full check-run detail page, not inline in the merge box): put the verbose receipt here (the full landing-rail verification transcript, links, timestamps), wrapped in a top-level `<details><summary>…</summary>` block. Note the GFM gotcha: a blank line is required immediately after `</summary>` or nested markdown (headers, code fences, lists) inside the collapsed block silently fails to parse and renders as raw text.
3. **Mirror as a single upserted PR issue-comment** (optional, needs `pull_requests: write`) for operators who live in the conversation tab rather than the Checks tab. Use the standard upsert pattern: embed a stable HTML marker (`<!-- glance-receipt:{pr-number} -->`) in the comment body, list existing issue comments filtered to the app's own bot login, and `PATCH` the matching one instead of creating a new comment per push: otherwise every re-check spams a new comment and buries the conversation.

Recommendation: ship the check-run alone for the wedge (it's the piece the ruleset can *require*); add the mirrored comment only if dogfooding shows operators aren't finding the Checks tab.

## What identifies a PR as agent-authored

No single universal signal exists. The wedge should check a fallback chain, in this order of reliability:

1. **PR author's GitHub login is a known bot account.** The strongest signal when it applies. Examples confirmed in the wild: GitHub's own Copilot coding agent authors as `copilot-swe-agent[bot]`, and it is *structurally* constrained to push only to branches under a `copilot/` prefix (GitHub enforces this; Copilot cannot push to `main`). Other agents follow the same bot-account convention but there is no registry; the wedge needs an allowlist, not a heuristic classifier.
2. **Head-branch naming convention.** `agent/*`, `copilot/*`, `devin/*`, `codex/*` style prefixes are common informal practice but are operator-chosen, not GitHub-enforced (except Copilot's branch-prefix restriction above). Useful as a secondary signal, or for repos that adopt a convention deliberately for the receipts-gate, but not something the wedge can assume exists on an arbitrary external repo.
3. **Commit trailer.** `Co-Authored-By: <Agent> <noreply@...>` is the most common convention (Codex defaults to `Co-authored-by: Codex <noreply@openai.com>`, Devin uses `Devin <bot@devin.ai>`), but it's advisory metadata a human can add or omit freely, and the ecosystem is still split on whether `Co-Authored-By` (implies human-equivalent authorship) or an alternative like `Assisted-by:`/`Coding-Agent:` is the semantically correct trailer. Treat it as a weak, spoofable signal.
4. **PR label.** The most robust *operator-controlled* signal for the wedge's own purposes. The receipt is generated by the glance daemon itself, which knows definitively whether it authored the PR, so the daemon can label its own PRs (e.g. `agent-authored`) or, more simply, just call the receipt endpoint only for PRs it created. No external detection is needed for the wedge's actual use case. The detection-signal question matters more for a *future* iteration where the App must decide, on an arbitrary third-party PR, whether to require the receipt. For the single-operator wedge (one external repo, glance is the only agent posting there), the question reduces to whether a receipt exists for this head SHA.

## How Aviator and Mergify attach to the same surface

Both are **installed GitHub Apps**, not GitHub Actions, which validates the App-based, zero-workflow-file approach:

- **Aviator (MergeQueue)**: installed as a GitHub App; core permission is to view/update/merge PRs it manages (adds a `ready-to-merge` label to enqueue), plus permission to touch `.github/workflows/*` (to merge PRs that modify workflow files) and to read branch-protection configuration. It reads the repo's *existing* required status checks (both required and non-required) and validates against them before allowing a merge. It does not post new checks by default; it consumes the ones already configured in branch protection/rulesets.
- **Mergify**: also an installed GitHub App. Reads the repo's branch protection rules and Rulesets automatically and translates them into its own internal merge conditions (e.g. a required-approvals rule becomes `#approved-reviews-by >= 1`). It *can* post its own check-run via a `post_check` action (using `checks: write`) to satisfy branch-protection requirements. This is the closest existing prior-art to what the wedge needs to build: an App-posted check-run that itself becomes a required check. Mergify explicitly cannot bypass GitHub's branch protection; it functions as a wrapper that must still satisfy the same gates a human merge would.

Neither product requires the target repo to add workflow files or grant Actions permissions. That confirms the App-only, zero-adoption path is the established pattern for this category of tool.

## Evidence

- [Permissions required for GitHub Apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps): `checks: write` needed for `POST/PATCH check-runs`; write access to the Checks API is App-only (OAuth apps/users cannot create check runs).
- [REST API endpoints for check runs](https://docs.github.com/en/rest/checks/runs): check-run schema, `output.summary`/`output.text` fields, states (`queued`/`in_progress`/`completed`), conclusions.
- [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) and [Managing a branch protection rule](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule): classic UI: restricting a required status check to a specific App requires that App to have already submitted at least one check run and be associated with a pre-existing required check.
- [Available rules for rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets): Rulesets' `required_status_checks` rule type, org-wide reuse, bypass lists.
- [REST API endpoints for repository rules](https://docs.github.com/en/rest/repos/rules): exact `required_status_checks` rule JSON shape: `parameters.required_status_checks[]` entries carry both `context` and optional `integration_id`; `strict_required_status_checks_policy` controls up-to-date-with-base enforcement.
- [Building a GitHub App that responds to webhook events](https://docs.github.com/en/apps/creating-github-apps/writing-code-for-a-github-app/building-a-github-app-that-responds-to-webhook-events): `check_run` webhook needs Checks read; write needed for `rerequested`/`requested_action` event types (the "Re-run" button).
- [Aviator: GitHub App Permissions](https://docs.aviator.co/manage/github-app-permissions) and [Aviator: MergeQueue](https://docs.aviator.co/mergequeue): permission list, "captures both required and non-required status checks... validates required status checks configured in GitHub."
- [Mergify: Security](https://docs.mergify.com/security/), [Mergify: Merge action](https://docs.mergify.com/workflow/actions/merge/), [Branch protection, Mergify's conditions, and repo permissions (discussion #5115)](https://github.com/Mergifyio/mergify/discussions/5115): `post_check` action posts a check-run; Mergify translates branch-protection/ruleset rules into internal conditions; cannot bypass branch protection.
- [About GitHub Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent) and [GitHub Copilot coding agent 101](https://github.blog/ai-and-ml/github-copilot/github-copilot-coding-agent-101-getting-started-with-agentic-workflows-on-github/): bot login `copilot-swe-agent[bot]`; branch-prefix (`copilot/`) push restriction enforced by GitHub itself, not just convention.
- [Attributing AI-Authored Commits in Git](https://crashoverride.com/resources/knowledge-base/code-ownership/attributing-ai-commits-git) and [Our coding agent commits deserve better than Co-Authored-By](https://fabiorehm.com/blog/2026/03/02/our-coding-agent-commits-deserve-better-than-co-authored-by/): survey of `Co-Authored-By` vs alternative trailer conventions (`Assisted-by`, `Coding-Agent`/`Model`) across Codex, Devin, and others; no consensus, all advisory/spoofable.
- [How to add a collapsible section in markdown](https://gist.github.com/pierrejoubert73/902cc94d79424356a8d20be2b382e1ab): `<details><summary>` GFM rendering rule: blank line after `</summary>` required for nested markdown to parse.
- [Checks API output text limit (github/docs#2403)](https://github.com/github/docs/issues/2403) and [safe-settings#493](https://github.com/github/safe-settings/issues/493): `output.summary`/`output.text` hard cap at 65,535 characters, enforced in bytes (multi-byte characters like emoji count against the byte limit, not the visible character count).
- [Branch Protection is Dead, Long Live Rulesets](https://wafaa-t.medium.com/branch-protection-is-dead-long-live-rulesets-1de78c35efca): community read on GitHub's steer toward Rulesets as the modern default (org-wide reuse, bypass-list audit trail, JSON import/export); corroborated by the official Rulesets docs above.
- [Create or Update Pull Request Comments in GitHub](https://benlimmer.com/blog/2021/12/20/create-or-update-pr-comment/) and [im-open/update-pr-comment](https://github.com/im-open/update-pr-comment): upsert-by-marker pattern for a single sticky PR comment instead of one-per-push spam.

## Open questions for the wedge build ticket (#337)

1. **Which repo is the pilot target, and who has admin rights to install the App and edit its Ruleset?** The wedge needs someone with repo-admin (or org-admin, if the target uses an org) to (a) install the App and (b) add the `required_status_checks` ruleset entry with this App's `integration_id`. Confirm this is a real capability we have on the chosen external repo before scoping #337, not something we need to request mid-build.
2. **App registration mechanics**: does glance already have a GitHub App registered anywhere (App ID + private key) that can be repurposed, or does #337 need to register a brand-new App via github.com/settings/apps/new? If new, decide the App's public name/description/icon now: it's user-facing the moment it posts its first check.
3. **Where does the daemon persist the App's private key and App ID?** Needs a secrets story consistent with the existing glance daemon secret-handling (env var / secret store): this wasn't scoped here and should be a #337 concern, not discovered mid-build.
4. **Receipt schema**: what fields does a "landing-rail receipt" actually contain (verification steps run, pass/fail per step, timestamps, links back to the daemon's own run record)? This brief assumes the receipt content already exists conceptually from the daemon's own landing pipeline: #337 needs the concrete schema before it can decide what goes in `output.summary` vs `output.text`.
5. **Stale-receipt invalidation**: v1 is push-only (daemon creates the check run once it finishes). If a human pushes an additional commit to the same PR after the receipt posts, the check run stays green against the old SHA unless the daemon (a) re-runs and re-posts on every push it's watching, or (b) the App subscribes to `pull_request: synchronize` and marks the existing check `neutral`/`stale` until a fresh receipt lands. Decide which before shipping, since a stale-but-green required check is worse than no gate at all.
6. **Does an App-posted review count toward "required approving reviews"?** Not verified in this pass: if a future iteration wants the "required reviewer" surface as a second layer, confirm whether GitHub counts a GitHub App's submitted PR review toward a ruleset's/branch-protection's approval-count requirement, or whether that surface is human-reviewer-only in practice.
7. **Multi-repo posture**: this brief is single-operator/single-repo by design per the campaign constraint. #337 should note where the "App installed on N repos, one Ruleset config per repo" model would need a management layer if the wedge proves out and gets asked to scale: not build it now, just don't paint the App registration into a single-repo-only corner (e.g., avoid hardcoding the target repo's owner/name anywhere the App's registration itself, since App installs are already naturally multi-repo-capable in GitHub's model).
